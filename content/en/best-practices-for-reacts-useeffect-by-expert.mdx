Cory House posted on X that the first argument to `useEffect` should be a named function, not an anonymous arrow. I followed the thread because that clashes with what shows up most often: the callback written inline.

An effect is readable sooner when the name says what it synchronizes. `syncSession` lands before a fifteen-line callback. People who disagreed called the name ceremony, and said a comment is enough.

House gives three reasons. I share them to different degrees:

- Code changes when the behavior changes. A comment does not. A comment that describes the effect from several refactors ago is lying.
- A named function shows up in the stack trace. The frame says `syncSession`, not an anonymous function. That shortens debugging and the error log.
- A comment completes the name when the name is not enough. It does not replace it.

The other complaint in the thread is that naming the effect makes it harder. The name adds no branches. It forces you to say what the effect does, and that shows when the effect was doing more than one thing.

I did not switch the callback to a named function. I keep the arrow and call a function declared outside it: `useEffect` runs `syncSession(userId)` and lists `userId` as a dependency. The effect body stays short, and `syncSession` can be tested without mounting the component.

The limit is the frame. If the exception is thrown from `syncSession`, the stack shows that name. If it is thrown from the arrow, that frame stays anonymous. Naming the callback itself, as House suggests, covers that case. For the effects I write, the outer function is enough.
