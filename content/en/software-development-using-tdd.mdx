A short note on working with TDD, after using it on a project. First, the cycle.

## What TDD is

Test-driven development is a design practice. You write a failing test, write the minimum code that makes it pass, and refactor while the test stays green. The cycle is red, green, refactor. The tests are usually unit tests. (Herranz, J. 2023) The same cycle can be used with an integration test.

![Diagram of the Test-Driven Development cycle: write a failing test, make it pass, then refactor](https://images.spiceworks.com/wp-content/uploads/2022/09/29095630/How-TDD-Works.png)

Image from Spiceworks.

## What it caught for me, and what it does not

I understand the person who says the test gets in the way because, once the function is done, they already saw it work. The test does not record that memory. It pins the behavior the code still has to meet when someone changes it, including you.

The compiler and the test catch different failures. If a user-schema change removes a property, TypeScript stops compiling even when no test exists. If the change alters what a calendar booking stores or which date it computes, and the two pieces look fine apart, the test for that behavior is what fails once they are combined.

The cost is development time, especially under a delivery deadline. In return, the regression shows up as a red test. TDD does not make the code scalable. It makes the broken behavior explicit.

Some projects do not pay that cost back. A one-day prototype is one. Code other people will modify is the case where I would use it again.

Herranz, Jose Ignacio. (April 13, 2023). TDD as a software design methodology. [paradigmadigital.com](https://www.paradigmadigital.com/dev/tdd-como-metodologia-de-diseno-de-software/).
