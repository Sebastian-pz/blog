I went back over JavaScript's execution model with Lydia Hallie's video. I had studied it before. This time I stayed with the relationship between the call stack and the event loop.

## The call stack

The call stack holds the frame of the function that is running and the frames of whoever called it. Each call pushes a frame. Each return pops one. The order is LIFO: the last frame in is the first frame out.

If a function keeps calling without returning, as in recursion with no base case, the stack grows until the engine aborts the run with a stack overflow.

## One thread, and when it blocks

In a browser realm, and on Node.js's main thread, that JavaScript has a single stack. Java and C# can run several threads at once. The runtime here does concurrent work — timers, network, disk — but the callback comes back to this stack. The event loop takes the next task when the stack is empty.

A long synchronous function holds the stack until it returns. In the browser, the next frame is not painted and a click is not handled while that lasts. On Node.js, the next callback does not run, including a `setTimeout` that has already come due. Async work waits on the queue. It does not run in parallel on that stack.

Web Workers, and `worker_threads` in Node.js, are another thread with their own stack. They do not change the main thread's model.
